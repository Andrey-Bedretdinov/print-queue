## Открыто

### 1. Превью для заданий из чужих программ — сделано в 1.8.0

Страница берётся из самой очереди: `Shot()` в `electron/main/spool.ts` читает
задание у спулера, `Pages()` разбирает контейнер, `Render()` играет страницу
`PlayEnhMetaFile` в растр в памяти и сохраняет PNG. Наружу это выходит через
`jobShot()` в `preview.ts` и канал `pq:job-shot`.

Проверено на живом задании (печать из браузера на HP через WSD): страница
получена за 1,25 с и совпадает с тем, что уходит на бумагу.

Не всякий драйвер спулит EMF: классовый HP отдаёт **XPS**, и разбор EMF на нём
возвращает `no-emf`. Для этого случая есть второй путь — `XPS` в `preview.ts`
открывает пакет через WPF и рисует страницу `RenderTargetBitmap`. Порядок такой:
сначала EMF, при `no-emf` — XPS.

Ограничения: у `RAW`-заданий нет ни того, ни другого — снимка не будет; крупное
задание читается заметное время, поэтому миниатюра берётся лениво, по наведению,
и кэшируется вместе с неудачей.

### Грабли этого захода

- **`Children.Add` возвращает индекс**, и он уходит в stdout поверх JSON —
  разбор падал с `helper-failed`. Правило №4 из CLAUDE.md в действии: любой
  вызов, что-то возвращающий, гасится через `$null =`.
- **Расширение из имени задания.** Спулер отдаёт `снимок.jpg (2640×1485)`, а
  Lightroom — `Lightroom (_MG_0114.CR2)`. Разбор по последней точке давал
  `jpg26401485` и `cr2)`, и файл переставал считаться снимком. Теперь общий
  `extOf()` в `shared/types.ts` берёт только первое слово после точки.

Ниже — исходный разбор, почему файла на диске нет и не будет.

**Не баг, а упершееся в стену ограничение.** На стенде в очередях лежало:

```
EPSON L8050 Series [сетевой], 38 | документ='Lightroom (_MG_0114.CR2)' | тип=NT EMF 1.008 | 16378540 байт
EPSON L8050 Series (копия 5), 30 | документ='Lightroom (_MG_0122.CR2)' | тип=NT EMF 1.008 | 16378484 байт
```

Печать шла из Lightroom мимо приложения. У спулера пути к файлу нет —
только имя документа, — поэтому миниатюре взяться неоткуда, и строка честно
показывает подпись с расширением.

Механизм `origins.ts` запоминает путь, только когда файл отправило **само
приложение** (перетаскивание в очередь, кнопка «+», выбор файлов). Для чужих
программ он не срабатывает и сработать не может.

Отдельно: `_MG_0114.CR2` — RAW Canon, `nativeImage` его не читает в принципе.
Lightroom печатает уже отрендеренный кадр, а исходник остаётся CR2.

**Проверить, что фича вообще жива:** перетащить в очередь обычный JPEG из
проводника — миниатюра и увеличение по наведению должны появиться.

**Как сделать превью и для чужих заданий.** Картинку брать не из файла, а из
самого задания — оно уже есть в виде EMF. Разбор контейнера на страницы готов:
`Pages()` в `electron/main/spool.ts`, и он же вынесен в
`tools/pq-spool-probe.ps1` для опытов. Дальше страницу надо проиграть не в
принтерный DC, а в memory-DC, и снять растр:

1. `CreateCompatibleDC(NULL)` + `CreateDIBSection` нужного размера (хватит 220 px
   по ширине, как у нынешних миниатюр).
2. `PlayEnhMetaFile` в этот DC.
3. Забрать биты и отдать в интерфейс тем же путём, что и `thumbnail()`.

Работы примерно на один заход. Ограничения: не сработает для `RAW`-заданий (там
нет EMF) и для очень крупных заданий будет заметно по времени — имеет смысл
считать миниатюру лениво, по наведению, а не для всей очереди сразу.

### 2. Перескок при переносе — починен, но не проверен вживую

Логика разобрана и исправлена (`src/App.tsx`, эффекты `settling`), но реальным
перетаскиванием не гонялась: для этого нужна автоматизация мыши **внутри** окна
приложения, а не просто по титульбару.

Проверять так: перетащить задание между блоками и смотреть, мелькает ли оно в
старой очереди после броска. Не должно.

Если понадобится автоматика — за образец годится `tools/pq-drag-test.ps1`, там
уже есть инжект мыши; надо только целиться не в титульбар, а в строку задания и
тащить её в другую колонку.

### 4. Мелочи

- Перенос через контекстное меню (`moveMany` в `src/App.tsx`) не имеет
  оптимистичной раскладки вообще — там тот же перескок, что чинили для
  перетаскивания, только без промежуточного состояния. Не трогал: сходу не
  просили, а трогать общий путь ради этого рискованно.
- Перетаскивание **внутри одной** системной очереди вызывает полноценный перенос
  задания на тот же принтер (`onDragEnd` не отсекает случай `from === to`). Работает,
  но делает лишнюю тяжёлую операцию ради смены позиции.
